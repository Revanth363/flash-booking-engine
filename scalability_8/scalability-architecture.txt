FLASH BOOKING ENGINE (FBE) - SCALABILITY & CAPACITY ARCHITECTURE

Document Status: APPROVED BASELINE (Google SDE-1 Standards)
Domain: Horizontal Scaling, Connection Sizing, and Load-Shedding Dynamics

1. DATABASE CONNECTION POOL MATHEMATICAL SIZING (PostgreSQL)
--------------------------------------------------------------------------------
PostgreSQL is a process-per-connection architecture. Setting pool size too high
degrades CPU performance due to operating system context-switching overhead.

Formula (PostgreSQL Official Engineering Standard):
  Max_Connections = ((Core_Count * 2) + Effective_Spindle_Count)

For a 4-Core PostgreSQL instance:
  Optimal_Total_DB_Connections ≈ (4 * 2) + 1 = 9 to 15 connections.

Multi-Node Slicing:
When running M stateless Go application instances behind Nginx:
  Pool_Per_Node = floor(Total_Database_Capacity / M)
With 2 Go instances and a 20-connection database ceiling:
  - Node 1: max_conns = 10 (8 booking semaphore slots, 2 reserved)
  - Node 2: max_conns = 10 (8 booking semaphore slots, 2 reserved)
Combined peak concurrent transactions = 16, comfortably below PostgreSQL saturation.

2. ADMISSION CONTROL & LOAD SHEDDING (LITTLE'S LAW: L = λ * W)
--------------------------------------------------------------------------------
If average reservation latency W = 10ms (0.01s):
  Max Throughput per node = 8 slots / 0.01s = 800 bookings/sec.
Across 2 Go nodes = 1,600 concurrent transactional reservations/sec.

When incoming traffic λ exceeds 1,600 req/sec:
- Excess requests hit the non-blocking semaphore channel in Go.
- Rejected in < 0.01ms with HTTP 503 (Retry-After: 1s).
- Protects memory footprint: RAM stays flat (< 25MB) under 50,000 req/sec spikes.

3. READ/WRITE TRAFFIC SEGREGATION (PHASE 2 BLUEPRINT)
--------------------------------------------------------------------------------
- Write Operations (Holds, Payments, Cancellations):
  Routed strictly to PostgreSQL Primary node via transaction-safe pgxpool.
- Read Operations (Viewing Seat Map, Event Discovery):
  Cached in Go RAM (W-TinyLFU) and Redis (Phase 2).
  Read misses routed to PostgreSQL Read-Replicas with Read-After-Write sticky session routing.
