FLASH BOOKING ENGINE (FBE) - CONCURRENCY & RACE CONDITION ANALYSIS
================================================================================
Document Status: ACTIVE DESIGN & ANALYSIS
Engineering Focus: Hot-row contention, Deadlock elimination, Atomicity

This document details the 7 true concurrency and race condition scenarios
from our 25 Master Scenarios, their failure modes, and technical solutions.

--------------------------------------------------------------------------------
1. SCENARIO 1 & 3: HOT-SEAT POINT CONTENTION & CONNECTION-POOL PROTECTION
--------------------------------------------------------------------------------
Problem:
1,000 users all attempt to reserve the exact same seat (e.g., "A1") at 11:00:00.000 AM.

Naive Failure Mode:
Using standard "SELECT ... FOR UPDATE" causes 1 user to acquire the lock and 999
transactions to queue in PostgreSQL lock memory. Even with NOWAIT alone, if 1,000 requests
all hit PostgreSQL simultaneously, they exhaust the database connection pool in Go,
causing connection acquisition timeouts and cascading latency spikes.

The 4-Layer Protection Architecture:

Layer 1 — Go Application Admission Control (Bounded Semaphore):
- A bounded semaphore (buffered channel of capacity N_booking_slots) limits how many
  booking transactions can enter the database path simultaneously per Go instance.
- Excess requests fail fast at the application gate with HTTP 503 Service Unavailable
  (Retry-After: 1s) in < 0.01ms without touching the database or allocating DB connections.
- Leaves reserved headroom in the pool for health checks (/readyz), payment webhooks,
  and background expiration workers.

Layer 2 — Bounded Connection Acquisition Timeout:
- pgxpool.Acquire(ctx) is called with a strict context deadline (e.g., 50ms).
- If an admitted request cannot acquire a physical connection within the deadline
  (due to temporary pool saturation), it fails immediately with HTTP 503 instead of
  queuing indefinitely in Go memory.

Layer 3 — PostgreSQL Row-Level Lock Abort (NOWAIT):
- SELECT ... FOR UPDATE NOWAIT.
- Once a connection is acquired, the transaction attempts to lock the requested seat row.
- If another transaction already holds the row lock, PostgreSQL immediately returns
  error 55P03 (lock_not_available) in < 1ms instead of queuing behind the lock holder.
- The Go engine catches 55P03, rolls back, and returns HTTP 409 Conflict to the client.

Layer 4 — Database Physical Integrity & Constraints:
- Partial Unique Index:
  CREATE UNIQUE INDEX idx_unique_active_seat ON bookings (seat_id)
  WHERE status IN ('HELD', 'PAID', 'CONFIRMED');
- Acts as the non-negotiable database-level guarantee against double-booking even if
  application-level checks or locks fail.

Initial Phase 1 Experimental Baseline (To Be Benchmarked):
- PostgreSQL connection pool per node: 10 connections
- Booking semaphore per node: 8 slots (leaving 2 reserved for health & payments)
- Connection acquisition timeout: 50ms
- Row-lock behavior: NOWAIT
- Excess admission response: HTTP 503 with Retry-After header
- Note: Cache is an optional optimization layer; PostgreSQL is the sole authority of truth.

2. SCENARIO 2 & 9: MULTI-SEAT BOOKING & CANONICAL DEADLOCK ELIMINATION
--------------------------------------------------------------------------------
Problem:
User X requests seats [A1, A2]. User Y simultaneously requests seats [A2, A1].
If Transaction X locks A1 and waits for A2, while Transaction Y locks A2 and waits
for A1, a circular wait deadlock occurs (PostgreSQL Error 40P01: deadlock_detected).

Production Solution:
- Canonical Lock Ordering: The Go business service sorts all requested seat IDs
  lexicographically/numerically BEFORE issuing any SQL statement.
  Both transactions will attempt to lock A1 first, then A2.
- User X locks A1 and A2. User Y fails fast on A1 via NOWAIT. Deadlocks are mathematically
  impossible because circular wait condition is eliminated.
- Atomicity: If any seat in the multi-seat batch is unavailable, the entire transaction
  rolls back immediately (all-or-nothing; no partial holds).

3. SCENARIO 4: GENERAL ADMISSION POOL ALLOCATION
--------------------------------------------------------------------------------
Problem:
A concert has 500 general admission tickets with no seat labels. 5,000 users attempt
to book quantities simultaneously.

Production Solution:
- Avoid "SELECT count(*) ... then UPDATE". That causes classic read-skew race condition.
- Use atomic decrement with a database CHECK constraint:
  UPDATE inventory_pools
  SET reserved_count = reserved_count + $requested_qty,
      version = version + 1
  WHERE event_id = $event_id
    AND (total_capacity - reserved_count - confirmed_count) >= $requested_qty;
- Check pgx RowsAffected():
  * If RowsAffected == 1: Allocation succeeded.
  * If RowsAffected == 0: Pool capacity exhausted; return HTTP 409 Sold Out immediately.

4. SCENARIO 5: THE "LAST TICKET" STAMPEDE IN THE POOL
--------------------------------------------------------------------------------
Problem:
Exactly 1 ticket remains in the pool. 1,000 users click "Book Now" at the same millisecond.

Production Solution:
- The same atomic conditional UPDATE statement executes:
  WHERE (total_capacity - reserved_count - confirmed_count) >= 1.
- Exactly 1 transaction satisfies the condition and increments the counter.
- The other 999 transactions evaluate the condition against the new committed value,
  find remaining == 0, and return RowsAffected == 0.
- Database constraint acts as the final defense:
  CONSTRAINT chk_pool_capacity CHECK (reserved_count + confirmed_count <= total_capacity).
- Guarantees zero negative inventory and zero overselling.

5. SCENARIO 7: PAYMENT VS. EXPIRATION RACE (THE 10-MINUTE ARBITER)
--------------------------------------------------------------------------------
Problem:
User pays at minute 09:59.900. Gateway responds at 10:00.100.
The background expiration worker runs at 10:00.000.
Did the user pay in time, or did the reservation expire?

Production Solution:
- Database transaction with row versioning (Optimistic Concurrency / Row Lock):
  UPDATE bookings
  SET status = 'PAID', version = version + 1, updated_at = NOW()
  WHERE id = $booking_id AND status = 'HELD' AND version = $expected_version;
- If worker committed first: status changed from HELD to EXPIRED. The payment UPDATE
  returns RowsAffected == 0.
- The payment engine detects: "Charge succeeded on gateway, but booking was EXPIRED."
- It initiates an automated compensatory transaction: triggers immediate refund
  record (REFUND_PENDING -> REFUNDED) and writes to audit log.
- Money is never taken without a ticket.

6. SCENARIO 15: THUNDERING HERD ON BULK EXPIRATION
--------------------------------------------------------------------------------
Problem:
50 reservations made at 11:00 AM expire at exactly 11:10 AM simultaneously.
A background worker releasing all 50 in a single giant lock locks the table,
while thousands of waiting users spam refresh.

Production Solution:
- Expiration worker runs in small, paced batches (e.g., LIMIT 20 SKIP LOCKED):
  SELECT id FROM bookings
  WHERE status = 'HELD' AND expires_at < NOW()
  LIMIT 20 FOR UPDATE SKIP LOCKED;
- Smooths inventory release over seconds rather than an instantaneous table-locking shockwave.

7. SCENARIO 19: GHOST CONFIRMATION (CANCELLATION VS. PAYMENT RACE)
--------------------------------------------------------------------------------
Problem:
User clicks "Cancel" at minute 05:00 while their bank payment webhook arrives
at the exact same microsecond.

Production Solution:
- Strict optimistic concurrency control on the booking row via "version" column.
- Cancellation and Payment both attempt conditional updates conditioned on version.
- First to commit succeeds; second fails the version predicate, inspects new state,
  and triggers automatic refund if payment lost to cancellation.
